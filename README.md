# SVOD

# СВОД — система учёта задач и времени

Корпоративный портал для конструкторского и производственного
подразделения. Сотрудники получают задачи, ведут таймер, уходят «в цех»,
сдают работу на приёмку. Руководители видят загрузку, следят за сроками,
принимают задачи, разбирают проблемные места. Начальник завода смотрит
свод по всем подразделениям. Администратор ведёт пользователей, роли,
отделы, бэкапы и следит за здоровьем системы.

**Стек:** Python 3.12+, Django 6.1, SQLite, gunicorn, whitenoise,
открытый CSS + лёгкий JS. Никаких SPA и тяжёлых фронтенд-сборщиков —
только серверный рендеринг и немного прогрессивного JS.

**Статус:** живой пилот. Схема БД и набор модулей активно развиваются.

---

## Для кого этот документ

- **Сисадмин**, который разворачивает портал — раздел «Запуск»
  и «Обслуживание».
- **Руководитель**, который хочет понять, что умеет система — разделы
  «Функционал» и «Механики».
- **Разработчик**, который будет дорабатывать — «Структура проекта»
  и «Разработка».

## Основные понятия

| Термин | Что это |
|---|---|
| **Задача** | Единица работы. Есть исполнитель, постановщик, срок, план часов, статус. |
| **Сессия работы** | Отрезок времени, когда сотрудник работал над задачей с включённым таймером. |
| **Сессия цеха** | Отдельный отрезок: сотрудник физически ушёл в цех. Не останавливает основной таймер. |
| **Заказ** | Договор на изделие. Есть 4 контрольные точки: контракт → старт проектирования → конец проектирования → отгрузка. |
| **Ветка заказа** | Направление работ внутри заказа (например, «Проектирование», «Производство»). Внутри — цепочка этапов. |
| **Этап** | Задача, стоящая в цепочке ветки на определённой позиции. Следующий этап запускается после закрытия предыдущего. |
| **Сдвиг плана** | Изменение сроков открытых задач исполнителя из-за срочной. Согласуется руководителем. |
| **Сверхурочная** | Запись «сотрудник X отработал N часов сверхурочно в день D». Вносит руководитель отдела. |
| **График работы** | Паттерн рабочих и выходных дней + часы в смене. Бывает личный, отдела, встроенный (5/2). |
| **Норма часов** | Сколько часов в день считается полной занятостью. Может отличаться по подразделениям. |
| **KPI** | Отношение плановых часов к фактическим. План/факт × 100%. Здоровая зона 90–110%. |
| **OTD** | On-Time Delivery — доля задач, закрытых в срок от всех закрытых. |

## Роли

Роли описываются моделью `accounts.Role`, а не хардкодом в коде. В каждом
подразделении может быть свой набор ролей. Есть стандартный набор,
который создаётся командой `init_roles`:

| Код роли | Название | Что даёт |
|---|---|---|
| `user` | Пользователь | Базовый доступ: свои задачи, чаты, кабинет |
| `staff` | Инженер-конструктор | То же + рабочий стол с таймером |
| `manager` | Руководитель подразделения | Кабинет руководителя, приёмка, отчёты отдела |
| `admin` | Администратор | Всё выше + админка портала `/settings/` |

Помимо кода роли, у каждой роли есть набор галочек (флагов),
которые включают отдельные возможности:

- `can_manage` — руководитель (кабинет, приёмка, отчёты отдела);
- `can_admin` — админ портала;
- `can_plant` — свод по заводу и оперативный монитор;
- `can_view_kpi`, `can_view_sessions`, `can_view_online`,
  `can_view_problems`, `can_view_task_logs`, `can_view_orders`,
  `can_view_analytics`, `can_export` — разделы кабинета;
- `is_developer` — технический раздел `/settings/dev/`.

**Начальник завода** — это роль с `can_manage=True, can_plant=True`.
Он видит свод по всем подразделениям, но не фиксирует доработки по
задачам отделов — это дело руководителя конкретного отдела.

**Суперюзер Django** видит всё независимо от роли и флагов.

## Функционал по ролям

### 1. Сотрудник

Основное место работы — **Рабочий стол** (`/`).

- Видит **фокусную задачу** — ту, что сейчас в работе. Или первую
  открытую, если в работе ничего нет.
- **Таймер** — живой, тикает каждую секунду. Рядом — «осталось до плана»
  и «сколько до дедлайна». Если план превышен — подсвечивается
  переработка.
- **Кнопки:** Начать, Пауза, На проверку, Выход в цех / Вернуться из цеха,
  Чат задачи, Описание.
- **Мои задачи** — остальные открытые задачи. Цвет кромки — приоритет.
  Дата красная — просрочено, оранжевая — сегодня.
- **Ждут моей приёмки** — задачи, где он постановщик и исполнитель сдал.
- **Часы за 14 дней** — график.
- **История закрытых** — последние закрытые задачи.

Дополнительно:

- **Постановка задачи** (`/tasks/create/`) — форма с чипами
  подразделений, типовыми задачами, календарями. Можно поставить
  задачу себе или коллегам, в том числе групповую (каждому создастся
  подзадача).
- **Реестр задач** (`/tasks/?view=tree|timeline|calendar`) — три вида:
  дерево декомпозиции, хронология (диаграмма Ганта), календарь сроков.
  Хронология доступна только руководителю и админу.
- **Чаты** (`/comms/`) — личные диалоги и чат по каждой задаче. Вложения:
  Ctrl+V для скриншота, drag-n-drop, кнопка 📎.
- **Уведомления** (`/notifications/`) — что произошло: назначили задачу,
  вернули на доработку, приняли, пришло сообщение.

**Личный кабинет** (`/me/`) — одна страница с вкладками:

- **Обзор** — счётчики, активная задача, сверхурочные за месяц,
  задачи на сегодня, последние сессии, последние задачи.
- **Мои задачи** — список с фильтрами по статусу, приоритету, сроку.
  Отметка 🚨 сверхурочная у задач, где есть сверхурочные записи.
- **Мои часы** — сессии работы и цеха за период.
- **Мой KPI** — план/факт часов, % в срок, эффективность, разбивка
  по дням. Экспорт CSV.
- **Мотивация** — рейтинг сотрудников месяца, уровень, стрик
  (дни без просрочек), достижения, кудосы, личное «зеркало»:
  динамика 8 недель, точность оценок по видам работ.
- **Мои действия** — журнал того, что сотрудник делал: возвраты,
  приёмки, изменения планов и сроков.
- **Профиль** — ФИО, отдел, роль, сверхурочные (все + за месяц),
  история входов.
- **Настройки** — тема (7 вариантов), размер шрифта (3 варианта),
  звук уведомлений, email-уведомления, утренний дайджест, фон
  (градиент / однотонный / мягкие пятна / сетка / свой цвет /
  своя картинка).

### 2. Руководитель отдела

Основное место работы — **Кабинет руководителя** (`/manager/cabinet/`).

- **Дайджест** одной строкой: закрыто за месяц, план/факт, OTD, KPI.
- **Главные плитки:** закрыто за месяц, план/факт, просрочено,
  в приёмке, OTD, перегружено сотрудников.
- **Очередь приёмки** — задачи на проверке. Можно принять или вернуть
  с комментарием. Виден исполнитель, факт часов, история возвратов.
- **Требуют решения: просрочен предыдущий этап** — блок с задачами,
  где предыдущий этап закрыт с опозданием. Руководитель выбирает:
  сдвинуть сроки этого этапа на N дней или активировать как есть.
- **Срочные не взяты 30+ минут** — задача с приоритетом «Срочно»
  назначена, но сотрудник её ещё не начал.
- **Уволенные с открытыми задачами** — блок с кнопкой «Переназначить».
- **«Требует внимания»** (сворачиваемый блок): просрочено > 7 дней,
  без движения > 14 дней, аномальные сеансы (ночные, сверхдлинные).
- **«Детали и аналитика»** (сворачиваемый блок): кто ломает план
  (топ исполнителей срочных), инициаторы срочных, топ по просрочке,
  топ по возвратам, топ отделов по просрочке, ресурс впустую
  (отменённые задачи с потраченным временем), ваш KPI, средний цикл.
- **График 8 недель** — сколько задач закрыто.

Отдельные страницы:

- **Команда** (`/manager/team/`) — таблица по каждому сотруднику:
  открытых, просрочено, часы за месяц, загрузка к норме, OTD, возвраты,
  KPI, план недели. Кнопка «Поблагодарить» прямо в строке.
- **Возраст задач** (`/manager/flow/`) — корзины 0–3 / 4–7 / 8–21 / 22+.
  Задачи в 8+ дней — кандидаты на разбор.
- **Загрузка отдела** (`/manager/workload/`) — сетка «сотрудник × неделя».
  Видно, кто перегружен, кто свободен. Часы открытых задач распределены
  по календарным дням интервала «старт → дедлайн».
- **Загруженность** (`/manager/load/`) — «нужно дней / окно дней → %».
  Плитки: перегружено / норма / резерв / без задач. Цвет:
  синий — резерв, зелёный — норма, красный — перегруз.
- **Приёмка** (`/manager/review/`) — очередь приёмки + причины
  возвратов за месяц.
- **Сессии** (`/manager/sessions/`) — журнал сессий работы и цеха.
  Сводка по людям. Экспорт XLSX / CSV.
- **Сверхурочные** (`/manager/overtime/`) — внести, изменить, удалить.
  Привязка к задаче опциональна. Экспорт CSV.
- **Отчёты** (`/manager/reports/`) — единый роутер. Параметры:
    - `period=month|quarter|year` — сводка за период;
    - `kind=analytics` — динамика и качество;
    - `kind=dynamics` — динамика отдела по дням (DailyDeptMetrics);
    - `kind=orders` — отчёт по заказам;
    - `kind=kpi` — KPI-отчёт по сотрудникам (Excel/CSV);
    - `kind=departments` — разрез по подразделениям (Excel/CSV).
- **Гант по заказам** (`/manager/orders/timeline/`) — контрольные точки
  заказов на одной шкале. Месяц / квартал / год.
- **Логи задач** (`/manager/logs/`) — журнал событий отдела. Фильтры
  по автору, задаче, типу, дате.
- **Онлайн** (`/manager/online/`) — кто активен за последние 15 минут,
  что делает, где простой.
- **Диагностика задач** (`/settings/problems/`) — 9 категорий проблем:
  без дедлайна, без плана, «в работе» без таймера, залипшие таймеры,
  зависшие на проверке / доработке, глубокая просрочка, заказ без
  ветки, план > 100 часов.
- **Карточка сотрудника** (`/manager/person/<id>/`) — открытые задачи,
  закрытые за месяц, часы, OTD, KPI (личный и управленческий),
  возвраты, график на 14 дней, отпуск.

### 3. Начальник завода (директор)

Роль с флагом `can_plant`. Видит свод по всем отделам.

- **Свод по заводу** (`/manager/plant/`) — таблица по всем
  подразделениям: люди, открыто, просрочено, закрыто, план/факт, KPI,
  OTD, отложенные срочные, ресурс впустую, возвраты, цех,
  сверхурочные, загрузка. Плюс блок сверхурочных за месяц
  с разбивкой по дням и отделам.
- **Оперативный монитор** (`/manager/plant/live/`) — «кто где прямо
  сейчас». Плитки: онлайн, в работе, в цеху, невзятые срочные.
  Карточки сотрудников с текущей задачей, минутами в цеху, просрочками.
- **Нормы часов** (`/manager/departments/hours/`) — управление
  глобальной и по отделам.
- **Графики работы** (`/manager/schedules/`) — создание, редактирование,
  привязка к отделам и сотрудникам. Предпросмотр на 28 дней.
- **Кто сегодня** (`/manager/schedule/today/`) — сводка по всем
  сотрудникам: работает / отдыхает / в отпуске, какой график
  применяется (личный / отдела / встроенный).
- **Динамика отдела** (`/manager/reports/?kind=dynamics`) — дневные
  срезы. Можно нажать «Собрать срез сейчас» — запустится
  `capture_daily_metrics`.
- **Аналитика по отделам** (`/manager/reports/?kind=departments`) —
  план/факт, OTD, эффективность в разрезе подразделений.
- **Отчёт по заказам** (`/manager/reports/?kind=orders`) — квартал / год,
  серии изделий, разрезы по отделам, медиана цикла
  «контракт → отгрузка».

### 4. Администратор портала

Роль с `can_admin=True`. Панель — `/settings/`.

- **Обзор** (`/settings/`) — счётчики, онбординг-чеклист, «Требует
  внимания», последние действия из аудита, топ просрочек, отказы
  входа за 7 дней.
- **Пользователи** — список с фильтрами (поиск, отдел, роль,
  активность, занятость). Массовые действия: активировать,
  уволить, сменить роль, отдел. Экспорт / импорт CSV.
- **Роли** — CRUD, права на разделы кабинета, флаг `is_developer`.
  Переназначение пользователей на другую роль.
- **Подразделения** — CRUD, привязка графика по умолчанию.
- **Типовые задачи** — название, план часов, срок.
- **Нормы часов** — глобальная норма.
- **Заказы** — CRUD, ветки, этапы.
- **Задачи** — общий список с массовыми действиями.
- **Журнал аудита** — кто, что, когда: модель, объект, JSON-изменения, IP.
- **Журнал входов** — успех / отказ, IP, User-Agent.
- **Уведомления админа** — алерты с дедупликацией, пороги,
  email-доставка.
- **Обращения в поддержку** — входящие, статусы, вложения.
- **Рассылки** — по всем / отделу / роли / админам, превью получателей,
  история.
- **Целостность данных** — 16 проверок (битые связи, дубли,
  «пользователь без роли», сессии с нулевой длительностью и т. д.).
- **Бэкапы** — создать снимок SQLite (`VACUUM INTO`), скачать, удалить.
- **Экспорт админки ZIP** — CSV всех справочников, логов и `meta.json`.
- **Пульт обслуживания** (`/settings/maintenance/`) — health-check,
  очистка старых записей, экспорт снапшота, endpoint для мониторинга.
- **Здоровье системы** (`/settings/health/`) — БД, диск, бэкапы,
  админы, алерты, AD. Форматы: HTML / JSON / text.
- **О системе** (`/settings/system/`) — версии, счётчики, ALLOWED_HOSTS,
  AUTH_BACKENDS, AD-настройки.
- **Диагностика задач** (`/settings/problems/`) — как у руководителя,
  но по всему заводу.
- **Обучение: статистика** (`/settings/onboarding-stats/`) — кто прошёл
  туры, где остановился, сброс прогресса.
- **Настройки алертов** — пороги отказов, окно, email.
- **Разработка** (`/settings/dev/`) — для роли `is_developer`.
  Версии, состояние планировщика, логи, модели.

### 5. Разработчик

Отдельный раздел `/settings/dev/` доступен при флаге
`Role.is_developer`, админу или суперюзеру.

- Версии Python / Django / ОС, режим DEBUG, БД, часовой пояс.
- Состояние планировщика (`logs/scheduler_state.json`).
- Health-check одной плиткой.
- Файлы логов и хвост последнего.
- Список моделей с количеством записей.

### 6. Общие сквозные функции

Работают у всех:

- **7 тем:** светлая, тёмная, графит, океан, тайга, песок, контраст.
- **3 размера шрифта:** компактный, обычный, крупный.
- **6 стилей фона:** градиент темы, однотонный, мягкие пятна, сетка,
  свой цвет, своя картинка.
- **Звук уведомлений** — Web Audio, генерируется прямо в браузере,
  без файлов.
- **Живые таймеры** — обновляются каждую секунду без перезагрузки.
- **Отсчёт до дедлайна** — цвет и текст меняются в зависимости
  от оставшегося времени и плана задачи.
- **Календарь** — встроенный, с подсветкой праздников РФ и переносов.
- **Универсальный модал подтверждения** — для всех `data-confirm` на
  формах и ссылках. Защита от случайного Enter.
- **Лайтбокс для картинок** — клик по изображению из `/media/`
  открывает его на весь экран.
- **Печать** — отдельный CSS для отчётов и списков.

## Механики

Здесь — «как оно работает внутри». Это важно понять, если ты будешь
эксплуатировать портал или дорабатывать.

### Жизненный цикл задачи

```
NEW ──▶ IN_PROGRESS ──▶ REVIEW ──▶ DONE
  │         │  ▲          │
  │         │  │          └──▶ REWORK ──┐
  │         │  │                        │
  │         └──┘  (pause / resume)      │
  │                                     │
  └─────▶ PENDING_APPROVAL ──▶ NEW ◀────┘
            (ждёт решения по сдвигу)
```

| Статус | Что значит |
|---|---|
| `NEW` | Создана. Таймер не запущен. |
| `IN_PROGRESS` | Идёт таймер. |
| `PAUSED` | Пауза. |
| `REVIEW` | Сдана на проверку. |
| `REWORK` | Вернули на доработку. |
| `DONE` | Закрыта. |
| `CANCELLED` | Отменена. |
| `PENDING_APPROVAL` | Задача-виновник срочного сдвига. Пока согласующие не решат — работать по ней нельзя. |

**Автостарта нет.** Таймер запускает исполнитель вручную. Это осознанное
решение: нельзя «включить» задачу человеку, который ещё её не открыл.

**Кнопки действий:**

- **Начать** (из `NEW`, `PAUSED`, `REWORK`). Запускает таймер.
- **Пауза** (из `IN_PROGRESS`). Закрывает сессию.
- **На проверку** (из `IN_PROGRESS`, `PAUSED`, `REWORK`). Закрывает
  сессию, уведомляет постановщика.
- **Выход в цех** — отдельная сессия, основной таймер не останавливается.
- **Задача решена** — для руководителя и админа. Закрывает задачу
  в один клик.
- **Отменить** — для руководителя и админа.

**Защита от двойных действий.** Если задача уже в `DONE`, её нельзя
снова «начать» или «принять». Кнопки не отрисуются, а прямой POST
вернёт сообщение об ошибке.

**Само-приёмка запрещена.** Если исполнитель и постановщик — один
и тот же человек, кнопка «Принять» не появится. Это страховка от
случая, когда сотрудник сам себе ставит задачу и сам же её принимает.

### Сессии работы и цеха

**TimeSession** — отрезок, когда сотрудник работал с включённым
таймером. Создаётся при паузе / сдаче / закрытии. Содержит:
`started_at`, `finished_at`, `duration_hours`, `status_at_close`,
опциональный `comment`.

**ShopSession** — отрезок, когда сотрудник ушёл в цех. Особенности:

- Не останавливает основной таймер. Оба идут параллельно.
- У сотрудника не может быть больше одной открытой цеховой сессии
  одновременно — это ограничение БД (`unique_open_shop_session_per_user`).
- Когда задача закрывается, сдаётся на проверку или отменяется —
  все активные цеховые сессии **закрываются автоматически**.
  Иначе они бы «повисли» и ломали диагностику.

Часы работы и цеха учитываются отдельно. Итог: `TimeSession` идёт
в KPI и план/факт, `ShopSession` — только в отчёт «Цех, ч».

### Дерево задач и декомпозиция

У каждой задачи есть поле `parent`. Дерево рисуется рекурсивно, до 6
уровней вложенности. В реестре (`/tasks/?view=tree`) у каждого узла
подсчитываются:

- сколько закрыто подзадач из общего числа,
- сумма плана и факта часов по всему поддереву.

**Кто может создавать подзадачу:**

- **Исполнитель** — только к своей **открытой** задаче.
- **Руководитель / админ / суперюзер** — к любой **открытой** задаче.
- К **закрытой** задаче — только через отдельную кнопку
  «Зафиксировать доработку» (см. ниже).

Это правило введено, чтобы нельзя было «в обход» прицепить новую
задачу к закрытой без фиксации доработки.

### Доработка к закрытой задаче

Отдельный флоу. Используется, когда задача закрыта, а по факту надо
что-то доделать.

**Кто может зафиксировать:**

- суперюзер,
- админ портала (`is_admin_role`),
- **руководитель отдела исполнителя** (не постановщик, не сам
  исполнитель, не руководитель другого отдела, не начальник завода).

**Что происходит:**

1. Появляется кнопка «🔧 Зафиксировать доработку» в карточке задачи.
2. Открывается модал: план часов (опционально), срок (опционально),
   обоснование.
3. Создаётся подзадача с тем же исполнителем, заказом, веткой,
   видом работы. Название: `[доработка] <исходное название>`.
4. В журнал исходной задачи пишется запись «Создана доработка #N».

Доработка **не входит** в цепочку этапов ветки — она «сбоку», чтобы
не сбивать порядок основного маршрута.

### Заказы: контрольные точки и этапы

Заказ описывается **четырьмя контрольными точками:**

```
контракт → старт проектирования → конец проектирования → отгрузка
```

Все они необязательные. Между ними считается **рабочих дней** — от
одной точки до другой. Полезно, чтобы планировать загрузку.

Текущий этап заказа (`stage_label`) — вычисляется по датам:

- прошла отгрузка → «Просрочена отгрузка»;
- прошёл конец проектирования → «В производстве»;
- прошёл старт проектирования → «Проектирование»;
- прошёл контракт → «Ожидает проектирования».

**Ветки заказа** (`TaskBranch`) — например, «Проектирование»,
«Производство». Внутри ветки задачи идут по `stage_order`. Логика:

- Первый этап ветки — активный.
- Следующие — `blocked_by_stage=True`, ждут.
- Когда текущий этап закрывается (или принимается) — следующий
  автоматически **разблокируется**, с него снимается `blocked_by_stage`,
  и исполнителю уходит уведомление.

**Если предыдущий этап просрочен.** Следующий **не разблокируется**
автоматически. Уходит в «ожидает решения руководителя»:

- у задачи проставляется `pending_shift_days = N` (сколько просрочено);
- `pending_shift_from_task` — ссылка на просроченный этап;
- уведомление постановщику и руководителям отдела исполнителя.

Руководитель открывает кабинет и решает:

- **Сдвинуть** — сроки этапа сдвигаются на N дней, этап активируется.
- **Активировать как есть** — этап активируется без сдвига.
- **Отложить** — этап остаётся заблокированным.

**Шаблоны маршрута.** Если у вас типовые заказы (например,
«Стандартный ГТ»), можно создать `OrderTemplate` с набором этапов,
и генерировать план заказа в один клик. Для каждого этапа задаются:

- точка отсчёта (одна из 4 контрольных точек),
- смещение в рабочих днях (плюс — позже, минус — раньше),
- длительность в рабочих днях,
- типовая задача (из неё берутся часы),
- роль исполнителя,
- ветка и позиция в ней.

Рабочие дни считаются по графику исполнителя — если у него 5/2
с производственным календарём, то учитываются праздники РФ; если
2/2 — только паттерн.

**Уведомления о контрольных точках.** Команда
`notify_order_deadlines` каждый день в 9:05 проверяет все заказы.
За **7 и 3 рабочих дня** до каждой контрольной точки ответственному
(`Order.owner`) уходит уведомление и email. Дедупликация — через
таблицу `OrderDeadlineNotification`: одна запись = одно отправленное
уведомление для (заказ, точка, «за сколько дней»). Если срок
перенесли — уведомление отправится заново по новому сроку.

### Сдвиг планов из-за срочных

Одна из ключевых механик. Работает так:

1. **Постановщик ставит срочную задачу.** При выборе приоритета
   «Срочно» появляется поле «Обоснование срочности» — обязательное.
2. **Создаётся заявка на сдвиг** (`PlanShiftRequest`). Она
   фиксирует:
    - задачу-виновника;
    - исполнителя и его отдел;
    - сколько рабочих дней нужно на срочную;
    - список открытых задач того же исполнителя, которые сдвинутся;
    - текущий уровень согласования.
3. **Задача-виновник уходит в `PENDING_APPROVAL`.** С ней нельзя
   работать, пока согласующие не решат.
4. **Согласующие на текущем уровне получают уведомление.**
   По умолчанию три уровня:
    - **Заместители отдела** — 2 часа,
    - **Руководитель отдела** — 4 часа,
    - **Начальник завода** — бессрочно.
5. **Первый ответивший решает:**
    - **Одобрить** → сроки открытых задач исполнителя пересчитываются.
    - **Ужать сроки** — открывается отдельная страница, где можно:
        - перекинуть часть задач на свободных коллег того же отдела
          и той же роли;
        - досрочно разблокировать следующий этап ветки;
        - разбить задачу-виновника на две подзадачи: часть выполнить
          сейчас, остаток отложить.
    - **Отклонить** → задача-виновник отменяется.
6. **Эскалация.** Если никто не ответил за таймаут, заявка уходит на
   следующий уровень. Команда `escalate_shift_requests` в планировщике
   проходит каждые 10 минут и эскалирует по `escalate_at`.

**Как считаются сдвиги.** У каждой задачи есть:

- `original_due` — срок на момент создания. **Никогда не меняется.**
- `planned_shift_days` — на сколько задача уже сдвинута.
- `due` — текущий срок.

Сдвиг считается всегда **от `original_due`, а не от текущего `due`**.
Это важно: сколько угодно пересчётов не накопят ошибку.

Формула:

```
window = рабочих дней от original_start_due до original_due
needed = ceil(plan_hours / норма исполнителя)
reserve = window − needed
shift = max(0, credit − reserve)
```

где `credit` — суммарная срочная нагрузка исполнителя
(`User.shift_credit_days`). То есть задача сдвигается на столько
дней, на сколько срочная «съедает» её запас по времени.

**Коррекция после закрытия.** Когда срочная закрывается, система
сравнивает факт с планом: `fact_days − planned_shift_days`.
Разницу досдвигает (если факт больше) или откатывает (если меньше).
Это позволяет более-менее автоматически поддерживать план
актуальным.

**Авто-пауза.** Когда исполнителю приходит срочная, его текущие
задачи в статусе `IN_PROGRESS` **автоматически ставятся на паузу** —
фокус переключается. В журнал каждой задачи пишется запись «Авто-пауза:
получена срочная задача».

### Сверхурочные

Отдельная сущность от сдвигов. Фиксирует руководитель отдела.

- Одна запись = один день = сколько часов сверхурочно.
- Привязка к задаче опциональна («на общие нужды» — например,
  аварийный ремонт, инвентаризация).
- Приложить приказ — файл, необязательный.
- `department` — снапшот на момент записи. Если сотрудника переведут
  в другой отдел, старая история останется за прежним.

**Кто видит:**

- Руководитель отдела — свой отдел, может вносить и править.
- Админ портала — все.
- Начальник завода — read-only, видит свод на `/manager/plant/`.
- Сотрудник — только свои, в `/me/?tab=profile`.

**Ограничения при вводе:** часы больше нуля, не больше 24 в сутки.

### Графики работы

`WorkSchedule` — паттерн рабочих / выходных дней + часы в смене.

Примеры паттернов:

- `[1,1,1,1,1,0,0]` — пятидневка;
- `[1,1,0,0]` — 2/2;
- `[1]*7 + [0]*7` — 7/7;
- `[1,1,1,0,0,0]` — 3/3.

`anchor_date` — день, когда цикл начинается «с первого элемента».
Для стандартной 5/2 это любой понедельник.

**Приоритет источников:**

1. `User.schedule` — личный график. Перебивает всё.
2. `Department.default_schedule` — график отдела.
3. Ничего — встроенная логика: пн–пт + праздники РФ.

**Флаг `use_calendar`:**

- **Включён** → праздники РФ и переносы **переопределяют** паттерн.
  Праздник → выходной, перенос → рабочий. Подходит для 5/2
  и офисных сотрудников.
- **Выключен** → работаем строго по паттерну. Праздник — обычная
  смена, оплачивается ×2. Подходит для сменных графиков (2/2, 7/7).

График используется **во всех** расчётах рабочих дней: при сдвиге
сроков, при определении «кто сегодня работает», при загрузке
отдела, при генерации плана из шаблона.

### Нормы часов

**Глобальная норма** — одна на весь портал (`core.Norm`). Указывает,
сколько часов в день считается полной занятостью. По умолчанию — 8.

**Норма отдела** — переопределение (`Department.hours_per_day`).
Например, для цеха со сменным графиком — 12 часов.

**Как выбирается норма** (`norm_hours_for(user)`):

1. Если у сотрудника есть отдел и у отдела задано `hours_per_day`
   больше нуля — берём его.
2. Иначе — глобальная `Norm.hours_per_day`.
3. Если ничего — 8.0.

Норма используется в KPI, в отчётах, в расчёте загрузки, при сдвигах.

### KPI и метрики

**KPI (личный):** `plan_hours / fact_hours × 100%`.

- `plan_hours` — сколько было запланировано.
- `fact_hours` — сколько фактически потрачено по сессиям таймера.
- Показатель включается при `fact_hours ≥ 1 час` — на меньших
  значениях метрика недостоверна.

**Здоровая зона — 90–110%.** Ниже — не уложились в оценку. Выше —
переработка (либо эффективность, либо заниженный план).

**KPI руководителя (композитный):**

- 40% — KPI отдела (план / факт по всем задачам отдела),
- 30% — OTD отдела (доля закрытых в срок),
- 20% — точность планирования (план / факт по задачам, где он
  постановщик),
- 10% — его личный KPI.

Если каких-то компонентов нет — веса нормируются.

**OTD:** доля задач, закрытых в срок, от всех закрытых, у которых
был срок. Задача считается «в срок», если `finished_at.date() ≤ due`.

**Эффективность:** `plan / fact × 100%`. Тот же KPI, но часто
показывается отдельно в отчётах по отделам.

**Точность оценок:** доля задач, где факт попал в план ±20%.
Если меньше 50% по виду работ — норма этого вида требует ревизии.

**Медианный цикл:** медиана дней «создана → закрыта».

### Мотивация

- **Уровни.** Стажёр → Специалист → Профи → Мастер. Считаются
  по сумме закрытых часов. Пороги: 0 / 20 / 60 / 150 часов.
- **Стрик (ритм).** Дни подряд без просрочек. Обновляется при
  закрытии задачи в срок. Рекорд хранится отдельно.
- **Достижения.** Первый результат, Скоростной, Снайпер, Надёжный,
  Неделя на ритме, Месяц на ритме. Выдаются автоматически по
  событиям.
- **Кудосы.** Благодарности от коллег. Руководитель может отправить
  прямо из таблицы команды. Самому себе — нельзя (ограничение БД).
- **Рейтинг.** Топ-20 сотрудников месяца по количеству закрытых задач
  и объёму плана. Медали за первые три места.
- **«Зеркало».** Личная аналитика: динамика за 8 недель, точность
  оценок по видам работ, следующий шаг — что взять в работу.

### Планировщик

Команда `python manage.py run_scheduler` держит фоновые задачи.
Запускается в отдельном процессе; в Docker — внутри контейнера `web`
при `RUN_SCHEDULER=1`.

**Интервальные задачи:**

| Команда | Интервал | Что делает |
|---|---|---|
| `escalate_shift_requests` | 10 мин | Эскалирует заявки по таймауту |
| `notify_overdue` | 30 мин | Уведомляет о появлении просрочки |
| `compute_idle_since` | 5 мин | Пересчитывает простой пользователей |

**По расписанию:**

| Команда | Время | Что делает |
|---|---|---|
| `cleanup_old_records` | 03:00 | Удаляет старые логи и записи |
| `load_ru_holidays` | 03:30 (1 и 15 числа) | Праздники РФ на текущий и следующий год |
| `send_daily_digest` | 09:00 | Утренний дайджест по email |
| `notify_order_deadlines` | 09:05 | Уведомления о контрольных точках заказов |
| `capture_daily_metrics` | 23:50 | Дневной срез по подразделениям |
| `capture_snapshot` | 23:55 | Снимок задач для диаграммы Ганта |

**Состояние** `SCHEDULED`-задач хранится в `logs/scheduler_state.json` —
это значит, что при перезапуске процесса задачи не выполняются
повторно.

**Остановка:** Ctrl+C или SIGTERM.

### Active Directory

Аутентификация через LDAP с NTLM-bind. JIT-создание пользователя
при первом входе. Маппинг групп AD → роли портала по словарю
`AD_GROUP_MAP` в `settings.py`.

**По умолчанию выключено** (`AD_ENABLED=0`). Пока не настроено на
проде — используется стандартный Django backend.

**Логика аутентификации:**

1. Пользователь вводит логин или email + пароль.
2. `ADBackend.authenticate()` делает bind к AD.
3. Ищет пользователя по `sAMAccountName` (если логин) или
   `userPrincipalName` / `mail` (если email).
4. Если нашёл — получает `displayName`, `mail`, `memberOf`.
5. Определяет роль по группам через `AD_GROUP_MAP`.
6. Если пользователя нет в БД — создаёт его с `set_unusable_password()`
   (вход через портал — только через AD).
7. Если пользователь есть — обновляет имя, email, роль.

**Скрипт проверки:** `scripts/check_ad.py`. Креды берутся из
переменных окружения `AD_TEST_USER` и `AD_TEST_PASSWORD` —
в код не вшиваются.

### Уведомления и email

**Внутренние уведомления** — модель `Notification` в `comms/`.
Создаются по событиям:

- назначена задача → исполнителю,
- задача взята в работу → постановщику и руководителю,
- выход в цех → постановщику и руководителю,
- сдано на приёмку → постановщику,
- принято → исполнителю,
- возврат на доработку → исполнителю,
- задача закрыта → постановщику.

На каждое — короткий текст и ссылка. Бейдж в шапке показывает
непрочитанное, обновляется каждые 5 секунд.

**Email-уведомления** — отдельная настройка в личном кабинете.
У каждого сотрудника два переключателя:

- **Письма о событиях** — новая задача, возврат на доработку,
  принято в приёмке.
- **Утренний дайджест** — одно письмо в 9:00 со списком дел на день.

Дайджест **не отправляется**, если у сотрудника нет задач на сегодня,
нет просрочек и нет задач на приёмке. Чтобы не спамить пустыми
письмами.

**Рассылки.** Админ может отправить письмо по сегменту: всем /
отделу / роли / только админам. Письма уходят по одному, в истории
сохраняется, сколько ушло и сколько упало.

### Вложения

Работают в трёх местах: в чатах, в задачах (прогресс и описание)
и в обращениях в поддержку.

**Ограничения:**

- Максимум 10 МБ на файл.
- Разрешённые расширения: PNG, JPG, JPEG, GIF, WebP, BMP, PDF, DOC,
  DOCX, XLS, XLSX, PPT, PPTX, TXT, CSV, ZIP, RAR, 7Z.
- MIME проверяется библиотекой `python-magic` (на Windows — через
  `python-magic-bin`).

**Способы загрузки:**

- Ctrl+V — вставить скриншот из буфера.
- Drag-n-drop на зону.
- Кнопка 📎.

### Темы, звук, фон

**7 тем:** light, dark, graphite, ocean, forest, sand, contrast.
Все цвета — через CSS-переменные, переключение мгновенное,
без перезагрузки.

**Звук:** генерируется в браузере через Web Audio API. Никаких

**Фон:** 6 стилей. Если выбран «Своя картинка» — загружается
файл до 5 МБ (PNG/JPG/WebP/GIF/BMP). Картинка отдаётся через

### Где какие данные

- **`db.sqlite3`** — основная БД. Локально — в корне проекта,
  в Docker — на volume `/data/db.sqlite3`.
- **`media/`** — загруженные файлы (картинки фона, вложения,
  приказы по сверхурочным). Локально — в корне, в Docker —
  на volume `/data/media`.
- **`backups/`** — резервные копии SQLite. Только на диске,
  через веб не отдаются.
- **`logs/`** — логи планировщика и `scheduler_state.json`.
- **`collected_static/`** — собранная статика (после
  `collectstatic`).
- **`static/`** — исходные css, js, шрифты, vendor.

### Безопасность в проде

При `DEBUG=0` включены:

- `SESSION_COOKIE_SECURE = True` — cookie только по HTTPS;
- `CSRF_COOKIE_SECURE = True` — CSRF-cookie только по HTTPS;
- `SECURE_CONTENT_TYPE_NOSNIFF = True` — не угадывать MIME;
- `X_FRAME_OPTIONS = 'DENY'` — запрет встраивания в iframe;
- **HSTS** на год (см. предупреждение ниже);
- `SECURE_PROXY_SSL_HEADER` — доверяем заголовку `X-Forwarded-Proto`.

**⚠️ Про HSTS.** Если включил HSTS и потом решил вернуться на HTTP
без сертификата — браузер **год не даст** зайти по http. HSTS надо
включать только когда портал реально работает по HTTPS с валидным
сертификатом.

**CSRF_TRUSTED_ORIGINS.** При работе за reverse-proxy на HTTPS —
обязательно перечислить домены в переменной
`DJANGO_CSRF_TRUSTED_ORIGINS`, иначе POST-формы (включая логин)
получат 403.

## Запуск на Windows (локально)

Подходит для разработки или чтобы «пощупать» систему.

### 1. Клонировать репозиторий

```powershell
cd C:\Users\<твой_пользователь>\OpenIDEProjects
git clone https://github.com/Trexx228/SVOD.git Timesheets
cd Timesheets
```

### 2. Создать виртуальное окружение

```powershell
python -m venv .venv
```

Активировать:

```powershell
.venv\Scripts\activate
```

В приглашении появится `(.venv)` — значит, окружение активно.

**Если PowerShell блокирует запуск скриптов** (`выполнение сценариев
отключено в этой системе`), разреши для текущей сессии:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

И снова активируй.

### 3. Установить зависимости

```powershell
pip install -r requirements.txt
```

**Что может пойти не так:**

- **`error: Microsoft Visual C++ 14.0 required`** при сборке
  `python-magic` — поставь Build Tools для Visual Studio
  (ссылка обычно есть в выводе ошибки). Или используй
  `python-magic-bin` (уже в requirements для Windows).
- **`pip` ругается на SSL / сертификаты** — обнови pip:
  `python -m pip install --upgrade pip`.
- **Долго скачивается** — это нормально, первая установка занимает
  1–3 минуты.

### 4. Создать `.env` (опционально, но рекомендуется)

```powershell
copy .env.example .env
```

Открой `.env` в блокноте и **замени `DJANGO_SECRET_KEY`** на что-то
своё. Секретный ключ можно сгенерировать так:

```powershell
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Скопируй вывод — это и есть ключ.

Остальные переменные можно не трогать, для локального запуска
подойдут дефолты.

### 5. Создать базу данных

```powershell
python manage.py migrate
```

Если всё ок — увидишь список применённых миграций и файл `db.sqlite3`
рядом с `manage.py`.

**Если ошибка про `DJANGO_SECRET_KEY`** — значит `DEBUG=0` в `.env`,
а ключ не задан. Поставь `DJANGO_DEBUG=1` в `.env` для локальной
разработки, тогда секретный ключ не обязателен.

### 6. Создать базовые роли

```powershell
python manage.py init_roles
```

Команда создаст 4 роли (`user`, `staff`, `manager`, `admin`)
и раскидает пользователей без роли.

### 7. Загрузить праздники РФ

```powershell
python manage.py load_ru_holidays --year=2026 --source=builtin
```

Команда работает без интернета и загружает стандартный список
переносов на год. Можно указывать два года подряд:

```powershell
python manage.py load_ru_holidays --year=2026
python manage.py load_ru_holidays --year=2027
```

### 8. Создать суперпользователя

```powershell
python manage.py createsuperuser
```

Спросят email, ФИО и пароль. Email — он используется для входа
(стандартный Django-логин заменён на email).

**Если пароль не проходит валидацию** — Django требует
не менее 8 символов, не слишком простой, не похожий на email.
Введите что-то вроде `Svod!Admin2026`.

### 9. Запустить сервер

```powershell
python manage.py runserver
```

Открой в браузере:

- **`http://127.0.0.1:8000/`** — портал.
- **`http://127.0.0.1:8000/admin/`** — Django admin.
- **`http://127.0.0.1:8000/settings/`** — панель управления порталом.

**Остановить:** Ctrl+C в терминале.

### 10. Хелпер `dev.bat`

В корне есть `dev.bat` — запускает всё одной командой. Что делает:

- активирует `.venv`;
- ставит `DJANGO_DEBUG=1` и `DJANGO_ALLOWED_HOSTS`;
- запускает планировщик в отдельном окне;
- запускает `runserver` с аргументами, которые передашь.

Использование:

```powershell
.\dev.bat runserver
```

Или без аргументов — тогда просто `runserver` с дефолтами.


Открой `http://<адрес_сервера>:8000/` из браузера. Если увидишь
страницу логина — всё хорошо.

Останови Ctrl+C и переходи к продакшен-запуску.

### 6. Продакшен: gunicorn

Создай systemd-юнит `/etc/systemd/system/svod.service`:

```ini
[Unit]
Description=SVOD Django Application
After=network.target

[Service]
Type=simple
User=www-data
Group=www-data
WorkingDirectory=/opt/svod
Environment="PATH=/opt/svod/.venv/bin"
EnvironmentFile=/opt/svod/.env
ExecStart=/opt/svod/.venv/bin/gunicorn \
    --workers 3 \
    --bind unix:/opt/svod/svod.sock \
    --access-logfile /opt/svod/logs/gunicorn-access.log \
    --error-logfile /opt/svod/logs/gunicorn-error.log \
    config.wsgi:application
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Перед запуском убедись, что папка `logs/` существует и доступна
пользователю `www-data`:

```bash
sudo mkdir -p /opt/svod/logs
sudo chown -R www-data:www-data /opt/svod
sudo chmod 755 /opt/svod
```

Активируй и запусти:

```bash
sudo systemctl daemon-reload
sudo systemctl enable svod
sudo systemctl start svod
sudo systemctl status svod
```

**Вариант B — в одном контейнере с web** (см. раздел Docker).

### 8. Nginx как reverse-proxy

`/etc/nginx/sites-available/svod`:

```nginx
server {
    listen 80;
    server_name svod.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name svod.example.com;

    ssl_certificate     /etc/letsencrypt/live/svod.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/svod.example.com/privkey.pem;

    client_max_body_size 12M;   # под вложения 10 МБ + запас

    location /static/ {
        alias /opt/svod/collected_static/;
        expires 30d;
        access_log off;
    }

    location /media/ {
        alias /opt/svod/media/;
        expires 7d;
        access_log off;
    }

    location / {
        proxy_pass http://unix:/opt/svod/svod.sock;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}
```

Активируй:

```bash
sudo ln -s /etc/nginx/sites-available/svod /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
```

**Важно:** если используешь HTTPS, не забудь
`DJANGO_CSRF_TRUSTED_ORIGINS=https://svod.example.com` в `.env`,
иначе POST-формы (включая логин) будут падать с 403.

## Запуск через Docker

Docker — самый быстрый и воспроизводимый способ для прода.

### Что есть в проекте

- **`Dockerfile`** — образ на базе `python:3.12-slim`, ставит
  зависимости, копирует код, переключается на `entrypoint.sh`.
- **`docker-compose.yml`** — описывает один сервис `web`, том
  `svod_data` для БД и медиа, пробрасывает порт `8000`.
- **`entrypoint.sh`** — что происходит при старте контейнера:
    1. `python manage.py migrate --noinput`;
    2. если `RUN_SCHEDULER=1` — запуск `run_scheduler` в фоне;
    3. `exec "$@"` — запуск gunicorn в foreground.

### 1. Подготовить `.env`

```bash
cp .env.example .env
nano .env
```

Для Docker важны:

```env
DJANGO_DEBUG=0
DJANGO_SECRET_KEY=<сгенерированный ключ>
DJANGO_ALLOWED_HOSTS=svod.example.com,web,localhost
DJANGO_CSRF_TRUSTED_ORIGINS=https://svod.example.com
RUN_SCHEDULER=1
```

Пути к БД и media **перебиваются** в `docker-compose.yml`:
они всегда `/data/db.sqlite3` и `/data/media` (это volume).

### 2. Собрать и запустить

```bash
docker compose build
docker compose up -d
```

Проверить:

```bash
docker compose logs -f web
```

Ожидаемый вывод: миграции, запуск планировщика, старт gunicorn на
порту 8000.

### 3. Первичная настройка внутри контейнера

```bash
docker compose exec web python manage.py init_roles
docker compose exec web python manage.py load_ru_holidays --year=2026
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py collectstatic --noinput
```

Портал — на `http://<адрес>:8000/`.

### 4. Остановить / перезапустить

```bash
docker compose stop      # пауза
docker compose restart   # перезапуск
docker compose down      # остановить + удалить контейнер (volume сохраняется)
```

### 5. Что важно знать про Docker

- **База данных** лежит в volume `svod_data` — при `down` она
  сохраняется. Удалить насовсем: `docker compose down -v`
  (⚠️ это сотрёт БД и media).
- **Планировщик** работает в том же контейнере, что и gunicorn.
  Если понадобится больше нагрузки — раздели на два сервиса
  (web и scheduler), оба с общим volume.
- **Порт** в `docker-compose.yml` — `8000:8000`. Если порт занят,
  поменяй на `8080:8000` или через `DJANGO_PORT` в `.env`.
- **Пересобрать после изменений в коде:** `docker compose build`
  и `docker compose up -d`.

## Переменные окружения

Все переменные читаются из окружения. В `.env.example` — шаблон.
В коде есть дефолты, но **для прода надо явно задать хотя бы
`SECRET_KEY`, `DEBUG=0` и `ALLOWED_HOSTS`**.

| Переменная | Назначение | Дефолт |
|---|---|---|
| `DJANGO_DEBUG` | `1` — dev, `0` — прод | `0` (или авто при `.dev-mode`) |
| `DJANGO_SECRET_KEY` | секретный ключ Django | обязателен в проде |
| `DJANGO_ALLOWED_HOSTS` | хосты через запятую | `127.0.0.1,localhost` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | origin'ы для HTTPS | пусто |
| `DJANGO_DB_PATH` | путь к SQLite | `BASE_DIR/db.sqlite3` |
| `DJANGO_MEDIA_ROOT` | путь к media | `BASE_DIR/media` |
| `DJANGO_SERVE_MEDIA` | `1` — раздавать media через Django | выкл |
| `DJANGO_EMAIL_BACKEND` | backend почты | console |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `SMTP_USER`, `SMTP_PASS` | SMTP | — |
| `SUPPORT_EMAIL` | адрес для обращений в поддержку | `admin@example.com` |
| `REGISTRATION_OPEN` | `1` — открыть саморегистрацию | `0` |
| `ALLOWED_EMAIL_DOMAINS` | домены для регистрации | `example.com` |
| `AD_ENABLED` | `1` — включить AD-аутентификацию | `0` |
| `AD_SERVER`, `AD_DOMAIN`, `AD_USER_BASE`, `AD_MAIL_DOMAIN` | параметры LDAP | — |
| `RUN_SCHEDULER` | `1` — планировщик в контейнере | `0` |

### Про email

По умолчанию backend — `console`. Это значит, что письма
**не отправляются, а печатаются в stdout**. Полезно для локальной
разработки: письмо видно в терминале, но реальный SMTP не нужен.

Для прода:

```env
DJANGO_EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_TLS=1
SMTP_USER=noreply@example.com
SMTP_PASS=<пароль>
SUPPORT_EMAIL=admin@example.com
```

Проверить, что письма уходят:

- Зайди в `/settings/alerts/settings/`.
- Укажи email для уведомлений.
- Нажми «Отправить тестовое письмо».

Если письмо не пришло — смотри логи Django и SMTP-сервера.

## Обслуживание

### Резервные копии

**Из админки:** `/settings/backups/` → кнопка «Создать бэкап».

Под капотом — `VACUUM INTO`: создаётся консистентный снимок SQLite
**без остановки сервера**. Файл появляется в `backups/`, оттуда
его можно скачать или удалить.

**Вручную (командой):** такой команды нет, но можно так:

```bash
python manage.py shell
```

```python
from admin_panel import backups as bk
name, size = bk.make_backup()
print(name, size)
```

**Расписание:** бэкапы **не делаются автоматически**. Рекомендую
поставить cron / Планировщик задач Windows:

**Linux cron** (`crontab -e`):

```cron
0 2 * * * cd /opt/svod && /opt/svod/.venv/bin/python -c "from django.core.management import call_command; call_command('dumpdata')" > /dev/null 2>&1
```

Или проще — сделай себе скрипт-обёртку и вызывай его.

**Windows:** Планировщик задач → запускай `dev.bat` с нужной
командой или `.bat`-файл, который вызывает `make_backup`.

**Что забрать в бэкап:**

- `db.sqlite3` (или `svod_data` volume).
- `media/` — вложения и картинки фона.
- `.env` — секретный ключ.
- `backups/` — если это копии на отдельном диске.

**Куда сохранять:** **на другой диск или сетевую шару**.
Если БД и бэкап лежат на одном диске и диск сдохнет — потеряешь
всё.

### Очистка старых записей

Накапливаются: журнал аудита, события входов, прочитанные алерты,
снимки хронологии. Команда `cleanup_old_records` чистит по политике:

- аудит — старше 180 дней;
- входы — старше 90 дней;
- прочитанные алерты — старше 30 дней;
- снимки хронологии — старше 400 дней.

**Запуск из админки:** `/settings/maintenance/` → «Очистить»,
или `/settings/system/cleanup/`.

**Параметры команды:**

```bash
python manage.py cleanup_old_records --audit-days=365 --logins-days=120
python manage.py cleanup_old_records --dry-run
```

`--dry-run` показывает, что будет удалено, и ничего не удаляет.
Рекомендую всегда сначала смотреть dry-run, потом чистить.

**Команда `cleanup_old_records` уже в планировщике** — 3:00
каждую ночь. Так что вручную трогать почти не придётся.

### Мониторинг

**Endpoint для Zabbix / UptimeRobot:**

```
GET /settings/health/?format=text
```

Ответ: `svod_health=ok` или `svod_health=warn` (обычный текст).

**JSON:**

```
GET /settings/health/?format=json
```

Возвращает `{"ok": ..., "critical_ok": ..., "warnings": [...],
"checks": {...}}`.

**HTML:** `/settings/health/` — удобно для визуальной проверки.

**Что проверяется:** БД, диск, бэкапы, число админов, непрочитанные
алерты, норма часов, AD.

### Обновление версии

**При работе без Docker:**

```bash
cd /opt/svod
sudo systemctl stop svod svod-scheduler
source .venv/bin/activate

git pull
pip install -r requirements.txt

python manage.py migrate
python manage.py collectstatic --noinput

sudo systemctl start svod svod-scheduler
```

**С Docker:**

```bash
cd /opt/svod
git pull
docker compose build
docker compose up -d
```

Миграции применятся автоматически через `entrypoint.sh`.

**Перед обновлением всегда делай бэкап.** Особенно если в релизе
есть миграции данных (а не только структуры).

## Типичные проблемы и решения

Собрано по реальным граблям, которые уже случались.

### `ModuleNotFoundError: No module named 'whitenoise'`

**Причина:** в `MIDDLEWARE` подключён `whitenoise`, но пакет
не установлен.

**Решение:**

```bash
pip install -r requirements.txt
```

Или выключи whitenoise из `MIDDLEWARE` в `config/settings.py`, если
не нужен.

### `ImproperlyConfigured: DJANGO_SECRET_KEY must be set`

**Причина:** `DEBUG=0`, а `SECRET_KEY` не задан.

**Решение:** либо `DJANGO_DEBUG=1` (для локалки), либо добавь ключ
в `.env`:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

### `django.db.utils.OperationalError: no such table: ...`

**Причина:** не применены миграции.

**Решение:**

```bash
python manage.py migrate
```

### CSRF verification failed (403 на POST)

**Причина:** при работе за HTTPS-прокси Django не доверяет origin'у.

**Решение:** добавь домены в `.env`:

```env
DJANGO_CSRF_TRUSTED_ORIGINS=https://svod.example.com
```

Перезапусти сервис.

### Статика 404

**Причина:** не собран `collectstatic`, либо Django не раздаёт
статику при `DEBUG=0`.

**Решение:**

```bash
python manage.py collectstatic --noinput
```

Убедись, что whitenoise в `MIDDLEWARE` (он раздаёт статику) или
что nginx настроен на `/static/`.

### Media 404

**Причина:** Django не раздаёт media при `DEBUG=0`.

**Решение:** либо nginx настроен на `/media/`, либо в `.env`:

```env
DJANGO_SERVE_MEDIA=1
```

И перезапуск. **Для прода лучше через nginx**, а не через Django.

### `SMTPAuthenticationError`

**Причина:** неверный логин / пароль / порт SMTP.

**Решение:**

- Проверь параметры в `.env`.
- Попробуй порт 465 с `SMTP_TLS=0` (SSL вместо STARTTLS) —
  некоторые SMTP-серверы работают так.
- Убедись, что у `SMTP_USER` есть право отправки писем
  от имени `DEFAULT_FROM_EMAIL`.
- Проверь, что firewall не блокирует исходящий трафик на порт.

### `python-magic` не находит libmagic

**Linux:**

```bash
sudo apt install libmagic1
```

**Windows:** обычно `python-magic-bin` из requirements решает
проблему. Если нет — установи Visual C++ Build Tools.

**Если вообще не нужен:** закомментируй проверку MIME в
`comms/views.py` в `upload_attach`.

### `SQLite database is locked`

**Причина:** SQLite плохо держит конкурентную запись. Обычно —
кто-то делает `VACUUM` в момент активных операций, или два
процесса пишут одновременно.

**Решение:**

- Убедись, что только один процесс пишет в БД. Например, не
  запускай второй `runserver` на том же `db.sqlite3`.
- Проверь, что планировщик один — не два.
- Если проблема повторяется и большая нагрузка — переходи
  на PostgreSQL (потребует доработки, но архитектура позволяет).

### Планировщик не запускается

**Причина:** команда `run_scheduler` не в PATH, либо процесс
падает сразу.

**Решение:**

- Запусти вручную: `python manage.py run_scheduler`. Смотри
  ошибки в stdout.
- Проверь, что `logs/` существует и доступна на запись.
- Проверь `RUN_SCHEDULER=1` в `.env`.

### Не работают уведомления / нет писем

- **В шапке нет цифры непрочитанных** — проверь, что работает
  `/comms/poll/` (открой в браузере, должен вернуть JSON).
- **Письма не приходят** — см. раздел «Про email». Проверь
  SMTP в `/settings/health/`.
- **Письма в спаме** — попроси админа добавить SPF/DKIM записи
  для домена отправки.

### Пользователь не может войти

- **«Неверный email или пароль»** — проверь пароль.
- **«Аккаунт не активирован»** — если регистрация открыта,
  пользователь должен кликнуть ссылку в письме. Если AD —
  должен пройти bind.
- **`DismissedUserLogoutMiddleware` принудительно выкидывает** —
  значит, пользователь помечен как уволенный / архивный.
  Проверь в `/settings/users/?status=all`.

### Задача не запускается — таймер не идёт

- Проверь, что статус не `PENDING_APPROVAL`. Такие задачи
  заблокированы до решения согласующих.
- Если задача `REVIEW`, `DONE`, `CANCELLED` — начать нельзя,
  см. жизненный цикл.
- Если задачу закрыл руководитель — её нельзя «доиграть».

### Пользователь уволился, а задачи остались за ним

- Открой карточку в `/settings/users/<id>/detail/`.
- Нажми «Переназначить задачи» → выбери нового исполнителя.
- Все открытые задачи перейдут на него, в лог каждой попадёт
  запись «Переназначение с ... на ...».

## Разработка

### pre-commit

В проекте настроены хуки, которые проверяют стиль перед коммитом.
Установка:

```bash
pip install pre-commit
pre-commit install
```

Теперь при `git commit` будут прогоняться:

- `yamllint` — чистота YAML.
- `flake8` — стиль Python (max-line-length=120).
- `end-of-file-fixer`, `trailing-whitespace` — убрать мусор.
- `check-yaml`, `check-json`, `check-toml` — синтаксис.
- `detect-private-key` — не залетели ли ключи.
- Локальный линт `.gitlab-ci.yml`.

Прогнать вручную:

```bash
pre-commit run --all-files
```

### `DEBUG` локально

Создай пустой файл `.dev-mode` в корне:

```bash
touch .dev-mode       # Linux/macOS
type nul > .dev-mode  # Windows
```

Django сам выставит `DEBUG=1`. Файл в `.gitignore` — на GitHub
не попадёт.

### Логи

При `DEBUG=1` ошибки видны прямо на странице. При `DEBUG=0` —
пишутся в логи gunicorn / systemd.

Логи планировщика: `logs/scheduler_state.json` + вывод
systemd-сервиса (`journalctl -u svod-scheduler -f`).

### Как тестировать локально

```bash
python manage.py test
```

Прогонит весь пакет тестов. Обычно занимает 30–90 секунд.

**Точечно по приложению:**

```bash
python manage.py test accounts
python manage.py test tasks
python manage.py test manager
python manage.py test admin_panel
python manage.py test cabinet
python manage.py test comms
python manage.py test core
python manage.py test dashboard
python manage.py test gamify
```

**Один тест-класс:**

```bash
python manage.py test manager.tests.ComputeLoadRowsTests
```

### Что покрыто тестами

- **`accounts`** — аутентификация, роли, права, scope, статус занятости,
  онбординг, туры.
- **`admin_panel`** — целостность, health, бэкапы, рассылки, аудит,
  импорт пользователей, `compute_idle_since`.
- **`cabinet`** — все вкладки личного кабинета, настройки, профиль,
  сверхурочные, KPI, мотивация.
- **`comms`** — чаты, поллинг, вложения, email, дайджест.
- **`core`** — нормы, типовые, праздники, рабочие дни, кэш.
- **`dashboard`** — фокус, cards, my_review, history scope, пятничный
  дайджест.
- **`gamify`** — каталог, ачивки, стрик, уровень, KPI.
- **`manager`** — доступ по ролям, кабинет, plant, отчёты, сессии,
  сверхурочные, графики, отпуска.
- **`tasks`** — создание, действия, urgent-сдвиг, дерево, timeline,
  шаблоны заказов, сдвиги планов, внешние сроки, отпускники.

Тесты **не ходят в AD** (в `settings.py` при `'test' in sys.argv`
принудительно ставится `AD_ENABLED=False`) и используют
`MD5PasswordHasher` для ускорения.

### Куда смотреть при доработке

- **Новые поля в модели** → `makemigrations` → `migrate`.
- **Новые URL** → в `urls.py` соответствующего приложения.
- **Новые команды** → в `management/commands/<name>.py`.
- **Новые фоновые задачи** → добавь в `TASKS` или `SCHEDULED` в
  `tasks/management/commands/run_scheduler.py`.
- **Новые флаги роли** → миграция + обновление `Role._has_flag`
  в `accounts/models.py` + `role_edit.html` + `admin_panel/views.py`.
